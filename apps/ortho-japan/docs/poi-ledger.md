## 1. 発端：三十三間堂が274mずれていた

施設チップの「三十三間堂」が実際の本堂（135.77175, 34.98795）から**274m西**に出る。
調べた結果、**当アプリのバグでも描画の問題でもなく、データセットの違い**だった。

```
optimal_bvmap-v1（当アプリ）        Anno  {vt_code:662, vt_text:"三十三間堂", vt_arrng:1} → 274m
experimental_bvmap（地理院地図Vector）label {annoCtg:662, knj:"三十三間堂", arrng:3}      →   3m
```

地理院地図Vectorが配信しているのは **experimental_bvmap**。当アプリが使う **optimal_bvmap-v1** は別製品（どちらも現役。experimental のタイルのほうが更新が新しい：`2026-06-18` 対 `2026-01-03`）。

## 2. ズレの正体：`arrng`（配置区分）の食い違い群だけが壊れている

京都中心部の1,773件を両者で1対1に突合した結果：

```
arrng 1→1（一致）  n=1613  中央値  0m           ← 大半は完全一致
arrng 2→2（一致）  n=  53  中央値  0m
arrng 1→3（不一致）n=  67  中央値 25m 最大393m   ずれは ほぼ真西
arrng 2→4（不一致）n=  40  中央値 33m 最大682m   ずれは ほぼ真北
```

ずれ量には規則がある：

```
国際交流会館 6字 393m ＝65m/字   無鄰庵庭園 5字 312m ＝62m/字
伏見稲荷駅   5字 302m ＝60m/字   三十三間堂 5字 275m ＝55m/字
```

**1字あたり約62m ＝ 1:25,000 の紙面で1字（2.5mm）が地上で占める長さ**。optbv側の点は「文字列の左端（横書き）／上端（縦書き）」を指しており、experimental側は別の基準点を指している。だから横書きは西へ、縦書きは北へ、ちょうど文字列1本ぶん流れる。

- 壊れているのは **1,773件中107件（6%）**。94%は0mで一致。
- **optbv単体では壊れている6%を見分けられない**（どちらも `vt_arrng:1`）。
- ズレは地上での固定量なので、画面上では z13→14px / z16→114px。低ズームでは見えない。
- 補足：この注記は `orgGILvl:"25000"`（1:2.5万図由来）。地理院地図Vector自身も**最大倍率では三十三間堂を消す**。

**副作用**：突合半径150mを外すため、タイルに注記があるのに「PLATEAU固有(d0)」と誤判定される組がある（例「椙本神社」「市立大野第一小学校」）。**位置を直すと種別の欠測も一緒に治る**。

## 3. experimental へ全面切替は不可（実測）

| 場所・ズーム | optimal | experimental | 倍率 |
|---|---|---|---|
| 京都 z8 | 92KB | **503KB** | 5.5倍 |
| 東京 z13 | 91KB | **727KB** | 8.0倍 |
| 京都 z15 | 31KB | **266KB** | 8.6倍 |
| 富士 z14 | 155KB | 377KB | 2.4倍 |
| 京都 z16 | 46KB | 82KB | 1.8倍 |

experimental は**建物を z13 から**（東京z13で `building:23,296`）、**等高線を z8 から**積む。optbv はそこを削った後継＝名前のとおり *optimal*。
さらに experimental には **`RdEdg`（道路縁）が無い**＝z16で道路が「白い面」になる今の見た目を作れない。
層名も属性名も別体系（`vt_text→knj` `vt_code→annoCtg` `WA→waterarea` `BldA→building` `RdCL→road` `Cntr→contour`）で、style4本・themes・decode・buildings・labels・shields が全部かかる。

→ **結論：基図は optbv のまま。注記の位置問題は POI台帳側で解決する。**

## 4. 設計：点は自前の台帳へ一元化

**線・面・地名系はタイル（optbv）のまま。点（施設）だけ自前で持つ。**

- 地名系（110/140/210/800）と交通系（421/422/411/412）は optbv で位置も正確・量も多い → 触らない
- 施設系（88x＋旧系統66x/53x/61x/63x/67x＋PLATEAU＋KSJ＋商業）→ 自前台帳
  - 位置は experimental を真実として採るので、**§2の6%問題は最初から存在しない**

### 器
- **z14タイル × GeoPBF**（`poi/14/x/y` の name 慣習でバケットから引く＝ローダ・IDBキャッシュ・gint経路は既存のまま）
- Workers静的アセットはファイル数上限があるが、**バケット配信なので無関係**
- **Morton は「並び順」として使う**（タイル内の座標デルタが縮む・gintのランク付き並びにそのまま乗る）
- 広域用に**全国版1本（上位ランクのみ・2万点≒700KB）**を併設＝海岸線と同じ扱い。z11以下はこれだけで足りる（今のランドマーク名札135棟はこの最上位バンドに吸収される）

### 1件のスキーマ
```
経度 / 緯度 / 種別コード / 名前 / ランク(1B) / 位置の出典 / 種別の出典 [ / 読み(kana) / 高さ]
```
- **住所は持たない**（実測：PLATEAU台帳で26%の件にしかなく0.36MB食う。必要なら町丁名レイヤで空間結合できる）
- **種別は文字列でなくコード**（用途の文字列は0.49MB→1バイトで0.03MB）
- **ランクは必須**：ズーム段階と衝突優先度を1つの数値で決める。建物は高さから、他は施設の格から焼く時に畳む
- **出典は属性ごとに分ける**（§5の理由）

### サイズ感（実測）
```
z14タイル1枚の文字つき注記：東京都心62 大阪66 福岡63 いの町48 京都36 札幌31 前橋30 富士17 淡路12 奥多摩7 → 平均37
日本の陸域 ≒ z14で77,000枚 → 全国150〜200万点、1件35B前後で50MB級、1タイル1.4KB
PLATEAU由来33,805点は4,378タイルに散る（平均7.7・最大108）
```

## 6. 種別は3段で決める。「不明」は埋めない

PLATEAU台帳33,805件で実測：

```
用途が不明/空 …………… 9,470件(28%)
  ├ 突合した注記コードあり 6,373件(67%) → 種別確定
  │   885学校2528 ／ 887郵便局1133 ／ 883警察913 ／ 422駅451 ／ 886病院312 ／ 880官公庁294 …
  └ 手がかり無し ……… 3,097件
       ├ 名前の接尾辞で分かる 1,769件(57%・ルール12本の雑な試作で)
       └ 最後まで不明 ……… 1,328件 ＝ 全体の3.9%
```

最後まで不明の中身は「すさみ町若者広場観光トイレ」「みろくゲートボール場」「若宮様」＝**そもそも名前を出す必要がないもの**。前方・部分一致のルールにすれば1%台まで落ちる。

**決定順序：① 突合した注記コード（最優先）→ ② 名前のルール表（数十行・人が読めて直せる）→ ③ その他（不明のまま・ランクを低く置いて描かない）。**
危険なのは推測で別の種別に入れること。不明は不明のまま安全に扱う。

## 7. 商業施設だけは構造的に維持不能 → 手管理

- **PLATEAU**：商業施設は559件(1.7%)、大型商業のキーワード一致は**全国19件**（イオンモール八千代緑が丘・イオンモール徳島・三井アウトレットパーク入間…）。埼玉の一部の市が偶然入力しただけで網羅の意思がない。
- **KSJ P33「集客施設」＝データ基準年月日 2014年11月30日**。12年前で使えない。
- **OSM** は網羅性・鮮度とも実用的だが **ODbL のシェアアライク**＝台帳に混ぜると全体が伝染する。混ぜない。

→ **地図に名前が出るべき規模（イオンモール級・駅ビル級・アウトレット級）は全国で数百件・増減は年に数件＝手で維持できる。**
そのための仕組み：
1. 系統ごとに独立して焼き直せる（出典を残す）
2. タイル単位＝焼き直しの影響範囲が閉じる
3. **手編集の差分レイヤ**（`poi-overrides.json`：追加・改名・削除）を焼き上げの最終工程で重ねる＝自動ソースが上書きしても手の修正が生き残る
4. geopbf の O(1) ヘッダ更新でタイルに版を刻む（いつ・どの系統で焼いたか）

## 11. スキーマ確定＋実装配置（2026-08-07・§8実測を受けて）

「焼く前に固める」を果たす。焼きは **`apps/uploader`**（ブラウザで geopbf が zip を直読み＝§9 の「Node で動かない」問題がここには無い。既存の `ksj()`/`admin()` が同型）。

### 11.1 uploader の独自DB＝2バケツで防火壁
| DB | バケツ | 中身 | header(license / attribution) |
|---|---|---|---|
| **civic核** | `GIS/poi/` | KSJ + PLATEAU + 注記 | 政府標準利用規約 / 国土数値情報・地理院 |
| **消費者** | `GIS/poi-osm/` | OSM + OpenChargeMap + Tesla | **ODbL / CC-BY-SA** / © OpenStreetMap・OpenChargeMap |

- **別バケツ＋別ヘッダ＝ODbL がバイトとライセンスの両方で civic に伝染しない**（§7「混ぜない」の実体）。焼き関数は2本＝`poi()`（civic）と `poiOSM()`（消費者）、どちらも `admin()` 模写。
- **消費者は「カテゴリごとに最良の開放源」**：コンビニ/飲食/宿泊/ガソリン/スーパー＝OSM（実測 名前98/89/92/91%・京都府）、**EV充電＝OpenChargeMap＋Tesla公式**（OSM は全国1,063件で桁不足＝EV だけ OSM が崩れる）。
- **メンテナンスのパス**：系統別に再クリックで焼き直し（KSJ 年次／OSM 月次 Geofabrik or Overpass／OCM 随時）＋ `poi-overrides.json`（手差分＝追加/改名/削除）を焼きの最終工程で合成 ＋ 版・日付を `updateHeader` に刻む。読み側 ortho-japan は `markers.js` の etag/Cache 型で新版を検知。civic 150〜200万点は「意味のある重いデータ」＝ bucket 永続が妥当（[[bucket-persistence-principle]]）。

### 11.2 器＝z≥14 の施設専用（低ズームは別枠が担当）
- **施設は z14 タイルからのみ出す。** 地名(110/210/800)・交通(422駅…)・地形は別トラック（optbv/DEM）が低ズームを持つ＝**POI台帳に全国 overview は不要**（§4 の「全国版1本」は撤回）。§8未決の「overview と z14 の切替」も消滅（切替が無い）。
- **格の全国ラダーも手管理の全国級リストも不要**になる（z≥14 ゆえ「清水寺を日本全図に出すか」の判断が発生しない）。
- 既存の高層ランドマーク帯（`plateau-landmarks`/far-DB・z11→150m）は**別枠のまま温存＝案A**。z14 で POI台帳と出会い、同名は既存 d2 ロジックで重複除去。スカイツリーは今まで通り z11 で見え、z14 から台帳が引き継ぐ＝回帰ゼロ。

### 11.3 1レコード（z14タイル内・実測で約19B／§4 の35B見積りより軽い）
`coords 2×uint16(タイル内ローカル・Morton順) / 種別 1B / rank 1B / 出典 1B(pos<<4|type) / 名前 varint長+UTF-8 [ / 読み / 高さ1B]`
- 住所は持たない・種別は文字列でなくコード・出典は属性別（§4/§5）。読みは駅など採れる系統だけ（88x帯の kana は空＝§5 の「読みは注記」は駅に限る）。

### 11.5 rank（1B・大きいほど重要・**役割は z14〜16 内の2つだけ**）
`rank = clamp( base[種別] + heightBonus, 0, 255 )`、`0`=描かない。`heightBonus = min(80, h/4)`（PLATEAUのみ・300m塔+75）。
- ① 衝突優先（密タイルでどのラベルが勝つか）② z14→16 の解禁段 `z_appear = 14 + (255-rank)*3/255`（都心 z14 タイルは注記37個・最大108個＝重要順に14→15→16で出す）。
- `base` は**同種内の粗い重み**でよい（郵便局>簡易局・総合病院>診療所・都道府県庁>市役所>町村役場＝KSJ区分から）。全国ラダーではない。

### 11.6 出典 enum（4bit×2）
`0 KSJ / 1 注記(experimental) / 2 PLATEAU / 3 手管理 / 4 名前ルール / 5 OSM / 6 OpenChargeMap`。位置採用の実優先 = **PLATEAU > 注記 > KSJ**（§8 追認）。

### 11.7 §8実測が確定させたルール（焼きに載せる）
1. **位置**：正規化名が一致する注記があれば注記位置（建物上）、無ければ KSJ 位置。
2. **正規化は系統別**：学校は「〇〇市立/区立/…」の自治体冠落とし（`normK`）が必須（10%→59%）。郵便局は既存 `norm0` で98%。
3. **注記885 = 小中高＋特支＋専修**。幼稚園/大学略記は別扱い（`P29_003` で分岐・大学は885に「◯◯大学キャンパス」名＋631に略記）。
4. **鮮度**：注記に当たらない＝廃止/移転の検出器（注記2026-06が錨）。

### 11.8 焼き手順（`poi()`＝`admin()` 模写）
1. KSJ 系統（v1 は P29学校・P30郵便局）を `geopbf(zip#inner)` でブラウザ直読み → 点＋分類＋住所。
2. 点が要求する experimental z16 label タイルを取得 → annoCtg で 位置採否・種別確定・鮮度判定（プローブ `scratchpad/poi-ksj-probe.mjs` のロジックを移植）。
3. 種別コード＋rank を付与 → z14 タイルへ分配 → タイルごとに geopbf 化 → `poi/14/x/y` で `save()`。
4. `updateHeader` に license/attribution/版。型が固まったら残り Pxx を同じ骨格へ。

## 12. 編集の方針確定（2026-08-10・本人裁定）

z14タイルへの施設集約は**編集方法まで含めて**設計する。§7「商業は手管理」と§11.1「poi-overrides（手差分）」を一本の編集ループとして確定させた。裁定は次の5点。

### 12.1 正本＝源流＋手差分。手差分は**ベクターファイルと分離してサーバー管理**（本人裁定の芯）
- z14 geopbf タイルは**焼き成果物**＝直接編集禁止。KSJ年次/OSM月次の焼き直しと手編集が構造的に衝突しない（タイル直編集だと次の焼き直しで手編集が蒸発する）。
- 手差分は**リポジトリのファイルでもタイル内でもなく、サーバー（native-bucket）側のレコード**として管理する。deploy と独立に編集が回り、本体ガジェット（www上で動く）から直接書ける＝gitに置くと編集がリポジトリ作業になってしまう。
- ノーサーバー原則（コスト非対称の堀）との整理：**読み手は今まで通り静的ファイルfetchのみ**。サーバー管理は書き手＝編集側だけの話で、堀は崩れない。

### 12.2 編集の入口＝ortho-japan本体の台帳編集ガジェット（desktop限定）
- 間違いを見つける場所＝直す場所。クリック→識別→追加/改名/移動/種別/rank/削除→サーバー台帳へ1レコード。
- ガジェット三戒準拠（独立・遅延ロード・抽象アクセス）。edit.html の人手ジオメトリ経路は臓器として移植可。
- 書き込み権限は当面本人のみ（bucket API key 保持者）。第三者編集の開放は別議論。

### 12.3 反映＝二段（即時パッチ→焼き込み）
- 表示側はタイルの上に**サーバー差分フィード**を重ねて即時反映（マニフェスト `index.json` と同じ軽さの器）。「編集して3秒後に地図が直る」が編集体験の芯＝焼き直し待ちにしない。
- 焼き直し便（系統別）が差分を合成してタイルへ焼き込む。**焼き込み後も差分レコードは消さない**＝履歴（巻き戻し・監査・次回焼きの再合成）。

### 12.4 同定＝タイルはIDなし19Bのまま・サーバーレコードに安定ID
- サーバー側レコードはサイズ制約が無い＝**安定IDを持つ**。削除（tombstone）もIDで確実に焼き直しを跨ぐ。
- タイル⇄差分の実行時マッチは正規化名一致∧300m以内（§0 同名クラスタ畳みと同じ閾値）。破れたらタイルへのID追加を再検討（それまで19Bの器を汚さない）。

### 12.5 防火壁・展開順序
- 手編集の出典は常に手管理(3)＝civic側。**OSMバケツは編集不可・丸ごと再生成のみ**。OSM値を見てcivicへ書き写すのは禁止（ODbL伝染）。
- 展開：**京都26で「焼き→表示→編集→焼き込み」を一周閉じてから全国へ**（P29+P30全国焼きは一周検証後）。器の手戻りを防ぐ。

### 12.6 手順（次の一歩）
1. サーバー台帳差分の器：bucket上のパス・レコードschema（id/op/name/ll/type/rank/出典/日付）・版の設計。
2. 表示側：差分フィードを `poiTiles` の上に被せる（`poiVer` 連動でラベルのみ再構築＝既存経路に相乗り）。
3. 本体編集ガジェット v1（追加/改名/移動/削除の4操作から）。
4. 焼き工程：uploader `poi()` 最終段でサーバー差分を合成（§11.8 の手順5として追加）。
5. 京都で一周検証 → P29+P30 全国焼き。

### 12.7 実装（2026-08-11・1〜4完了＝残は5の一周実地検証）
- **器**＝`GIS/pbf/poi/overrides.json` 1本（civic専用）：`{v:版, seq:次id, recs:[{id,op,n,ll,to?,t?,r?,d}]}`・op=add/move/rename/del。
  意味論の正典＝`uploader/src/poi/schema.js applyOverrides`（match=名前完全一致∧300m最近傍・id昇順fold・moveはposSrc手管理へ）。
  空の台帳を初期化済み（表示側の404ゼロ維持）。
- **表示**＝app.js `applyPoiOvr`＋`poiPatchedAll`（実行時パッチ・poiVer連動）。権威＝注記(1)に**手管理(3)を追加**＝
  add/moveした点は基図同名を上書き。`tests/t-poioverrides.mjs` が焼き側との**同値を機械検証**（17項目・t-chome方式の実ソース切り出し）。
- **⚠設計で塞いだ穴（テストが検出）＝墓標の再発火**：焼き込み後に同じrecを再適用すると、del/move が「対象は焼きで
  消えた/動いた」まま同名近傍(≤300m)の**別施設**を最近傍matchで誤爆する。→ 焼きは効いたrec idを**マニフェスト
  `baked`** に記録（既存と合流）・表示は未焼き分だけ適用。タイルとbakedは同じマニフェスト便＝新旧が食い違わない。
