Ortho Earth 2.0 を公開しました

古い口を捨てて、TypeScript で建て直した

2026-10-17 · @ortho-earth/globe · @ortho-earth/core · @ortho-earth/japan · geopbf

地球儀の地図エンジン @ortho-earth/globe と、それを支えるパッケージを 2.0 にしました。 見た目はほとんど変わっていません。地球は前と同じように回り、多くのコードは import もそのままで動きます。 変わったのは、見えない下回りです。ソースをすべて TypeScript に移し、1.x が「念のため」に残していた古い呼び名や裏口を、この機会に外しました。

この工房には「新しい概念に入るときは、古いものを捨てよ」という決まりがあります。 互換のための別名は、残しておけば誰も困りません。でも、残すたびに「どちらで書けばいいのか」という迷いが一つ増えます。 2.0 は、その迷いを片付けるための版です。

1. 何が変わったか

  • ソースは TypeScript（strict）。型はソースから作ります。移してみると、1.x の手書きの型と実際のコードが食い違っている所が、思ったよりたくさん出てきました。型にはあるのに実体に無い名前、その逆。どれも実体の側に合わせて直しました。import の書き方は変わりません。
  • 公開の口は、名前を挙げたものだけ。1.x は src/ のどのファイルでも読めました。便利でしたが、中の作りを変えるたびに、誰かのコードを壊すおそれがありました。2.0 は各パッケージの exports に並ぶサブパスだけを出し、internal/* は閉じました。
  • 古い呼び名を外した。plateau は mesh に、maxPitch は常に度（MapLibre と同じ）に、addCOPC は addPointCloud に。自作ガジェットは map.registry.gadgets.add(name, (map, ...args) => handle) で登録し、本体は map を第 1 引数で受けます。this が何を指すか、もう悩まなくて済みます。
  • 新しいパッケージ。React の部品 @ortho-earth/react、Google の写実 3D Tiles @ortho-earth/google-tiles、KTX2 のテクスチャ @ortho-earth/ktx2、大量の模型・看板・3D の文字の @ortho-earth/plugin-scene、Gaussian splat の @ortho-earth/plugin-splat を初めて公開しました。

2. 入れ方

npm i @ortho-earth/globe

latest は 2.0 です。最初の地図の出し方は Get started に、MapLibre GL JS や CesiumJS のコードから移る道は MapLibre から・CesiumJS から にあります。

3. 1.x から移る・1.x を使い続ける

書き換えが要る所は、パッケージごとに「1.x の書き方 → 2.0 の書き方」の表にまとめました： MIGRATION.md（1.x から 2.0 への移行）。表に無い API は 1.x と同じです。

1.x のままでいたい場合

版の範囲で指定します：npm i @ortho-earth/globe@1（geopbf なら geopbf@1）。 1.x のソースは GitHub のブランチ v1 に残してあります。 コードの古い口は捨てましたが、配った URL や QR は捨てていません。l= のローマ字キーや lang=jp など、URL の古い書き方は 2.0 でも読み続けます。一度人に渡した地図は、壊さないのが作法だと思っています。

4. 出してから見つかったこと

正直に書くと、2.0.0 を出した後にも直しがありました。きっかけの多くは、PLATEAU の 3D 建物を MapLibre GL JS（deck.gl）・CesiumJS・Navara・TerriaJS と同じ条件で表示して比べる、性能の測定です。 他のエンジンと並べて測ると、自分だけを見ていた時には気づかなかった癖が、数字になって出てきます。2.0.2（2026-10-19）では次の所を直しました。

  • worker の中で @loaders.gl 4.5 と組むと、b3dm の 3D Tiles が描けていませんでした。比べるページを組む中で、ortho-earth だけがこの組み合わせで建物を描けないと分かりました。
  • 世界の塗りや標高の索引を切った地図でも、それらを取りに行っていました。使わない物は取りに行かないようにしました。
  • 起動時の描き直しを束ね、3D Tiles は兄弟のタイルが揃ってから塊で出すようにしました。描画 worker の空回りも止めました。

測定そのものも面白い結果になりました。同じ「60 fps」でも、エンジンごとに中身がまるで違います。動いている間はタイルを読まずに滑らかさを保つもの、スマホでは絵を粗くして軽くするもの、読みながら描くもの。どこで手を抜くかに、それぞれの設計の考え方が出ていました。 詳しくは PLATEAU 3D 都市モデルの描画性能比較 にまとめました。
